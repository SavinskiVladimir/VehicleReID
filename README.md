# Vehicle Re-ID

Система поиска транспортных средств по изображению (дипломная работа).
Пользователь загружает кадр, система находит на нём ТС, пользователь
выбирает нужное, и по векторному признаковому описанию находятся
наиболее похожие наблюдения в базе.

```
 браузер ──► frontend (React, :3000) ──► backend (FastAPI, :8000) ──► PostgreSQL + pgvector
                  Vite-прокси /api              │
                                                ├─ детектор YOLO11s   (ONNX)
                                                └─ ReID EfficientNetV2 (ONNX, эмбеддинг 512)
```

## База наблюдений и история поиска - две разные сущности

| | **База наблюдений** (вкладка «База наблюдений») | **История поиска** (вкладка «История поиска») |
|---|---|---|
| Что это | записи, **в которых ищем** (галерея) | журнал выполненных поисков: **что искали** |
| Пополняется | осознанно: кнопка «Сохранить как наблюдение», пакетная загрузка (функция 8 ТЗ) | автоматически при каждом поиске (функция 9 ТЗ) |
| Таблица | `observations` | `search_queries` |
| Что хранится | изображение, кроп, рамка, вектор, время | кроп запроса, рамка, вектор, время, итог (сколько найдено, лучшее совпадение) |
| Действия | просмотр, удаление (админ) | просмотр, **повторный поиск**, удаление и очистка (админ) |
| Объём | до 100 000 записей | последние `SEARCH_HISTORY_MAX_ITEMS` (500), старые удаляются вместе с файлами |

Повторный поиск из истории идёт **по сохранённому вектору** и по **текущему** содержимому базы: исходное изображение и ML-модели не нужны, а результат может отличаться от
исходного (в базе могли появиться или исчезнуть записи). В историю повтор не записывается. Если запись в историю не удалась, сам поиск всё равно возвращает результат.

История общая для всех посетителей (учётных записей пользователей в системе нет), поэтому удаление и очистка - только с токеном администратора.

## Структура

| Папка | Назначение |
|---|---|
| `backend/` | API на FastAPI: сервисы (детекция, предобработка, эмбеддинг, поиск), слой БД |
| `frontend/` | веб-интерфейс (React + Vite), подробности - `frontend/README.md` |
| `ml/detection/`, `ml/reid/` | обучение, оценка и экспорт моделей |
| `db/` | инициализация БД: расширение, таблица, HNSW-индекс |
| `scripts/` | `ingest_images.py` - пакетное пополнение базы; демонстрационные `demo_search.py`, `demo_populate_db.py` |
| `tests/` | тесты (pytest), запускаются из корня проекта |
| `docker-compose.yml` | база данных (PostgreSQL с pgvector) |

## Требования

- Python 3.12, Node.js `^20.19` или `>=22.12`
- Docker (на Windows - Docker Engine внутри WSL2) для PostgreSQL
- Обученные и экспортированные модели (шаг 5)

## Запуск с нуля

Все команды - **из корня проекта**, если не сказано иное.

**1. Настройки**
```powershell
Copy-Item .env.example .env
```
Откройте `.env`: как минимум смените `ADMIN_API_KEY`, при занятом порту -
`POSTGRES_PORT` (и тот же порт в `DATABASE_URL`). Описание всех
параметров - в самом `.env.example`.

**2. База данных** (в терминале, где доступен Docker; на Windows - Ubuntu в WSL2)
```bash
docker compose up -d db
docker compose ps        # дождаться статуса healthy
```

**3. Зависимости backend**
```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r backend\requirements.txt
```

**4. Схема БД** (один раз)
```powershell
python db\create_table.py
python db\create_indexes.py
```
Если база уже была создана более ранней версией скриптов, `create_table.py` безопасно
запустить повторно: он добавит только недостающие таблицы (например, `search_queries` для
истории поиска) и **не трогает** существующие данные.
Индекс обязателен для требования ТЗ "поиск не более 30 мс на 100 000 записей":
без него поиск работает полным перебором (сервер при этом работает, но
предупредит об этом).

**5. Модели** - положить экспортированные ONNX-файлы туда, где их ждёт backend:
```powershell
# детектор -> ml/detection/exported/vehicle_detector.onnx
python ml\detection\export_detector.py --checkpoint ml\detection\runs\vehicle_detector\weights\best.pt --output ml\detection\exported --imgsz 640

# ReID -> ml/reid/exported/reid_embedder.onnx (запускать ИЗ папки ml\reid)
cd ml\reid
python export_reid.py --checkpoint checkpoints\best_checkpoint.pt --output exported --imgsz 224 224
cd ..\..
```
Размер `--imgsz` ReID-модели должен совпадать с `REID_IMAGE_HEIGHT/WIDTH` в `.env`.

**6. Backend**
```powershell
uvicorn backend.app.main:app --reload
```
При старте сервер проверяет согласованность конфигурации: файлы моделей на
месте, размерность эмбеддинга модели равна 512 (как в колонке БД), состояние
БД. Если что-то не так - он либо не запустится с понятным сообщением
(модели), либо запустится и сообщит в логе и в `/health` (БД).

**7. Frontend** (в другом терминале)
```powershell
cd frontend
npm install
npm run dev
```
Открыть `http://localhost:3000`.

**8. Проверка**
```powershell
curl http://127.0.0.1:8000/health
```

| Поле ответа | Что значит |
|---|---|
| `status: "ok"` | БД доступна, расширение `vector` и таблица `observations` на месте |
| `status: "degraded"` | чего-то не хватает - причины и что делать в `problems` |
| `warnings` | не мешает работе, но влияет на скорость (например, нет HNSW-индекса) |
| `schema.*: null` | БД недоступна, про схему ничего не известно |
| `schema.search_history_table: false` | нет таблицы истории поиска: поиск работает, но история не пишется (`python db\create_table.py`) |
| `embedding_dim` | размерность эмбеддинга загруженной ReID-модели (должна быть 512) |

Документация API с возможностью пробовать запросы - `http://127.0.0.1:8000/docs`.

## Пакетное пополнение базы наблюдений

Базу можно наполнять не только кнопкой «Сохранить как наблюдение», но и сразу папкой изображений.
Скрипт проходит тот же путь, что и интерфейс (детекция, кроп, эмбеддинг, постоянное хранилище, БД), но без участия пользователя:

```powershell
# сначала посмотреть, что будет загружено, ничего не записывая
python scripts\ingest_images.py data\frames --dry-run

# загрузить кадры камер (каждое найденное ТС - отдельное наблюдение)
python scripts\ingest_images.py data\frames

# загрузить готовые кропы машин, например VeRi-776 (детектор не нужен)
python scripts\ingest_images.py data\VeRi\image_test --mode whole --limit 500
```

| Режим `--mode` | Что становится наблюдением | Детектор |
|---|---|---|
| `all` (по умолчанию) | каждое ТС, найденное на кадре | нужен |
| `best` | только самое уверенное ТС кадра | нужен |
| `whole` | кадр целиком (для готовых кропов) | **не нужен** |

- **Повторный запуск безопасен.** Файл опознаётся по хешу содержимого: прерванную загрузку просто запустите снова, добавится только недостающее. Переименованные и скопированные картинки дубликатов не создают. Копии внутри одного запуска тоже обрабатываются один раз.
- **Загрузить заново с другими настройками:** `--replace` (например, `--mode best --replace`). Старые наблюдения файла и их файлы заменяются новыми, а не накапливаются.
- **Один файл - одна транзакция.** Сбой модели или БД посреди кадра не оставляет ни записей без файлов, ни файлов без записей: или загружены все ТС кадра, или ни одного.
- Остальные параметры: `--limit N` (пробный запуск), `--confidence`, `--no-recursive`, `-v` (результат по каждому файлу). Справка: `python scripts\ingest_images.py --help`.
- Код возврата: `0` - всё хорошо, `1` - не удалось начать (нет модели, БД, таблицы, пути), `2` - часть файлов не загружена (список в конце, остальные загружены), `130` - прервано (Ctrl+C), можно продолжить повторным запуском.

Перед первым запуском нужна таблица учёта загрузок: выполните `python db\create_table.py` (добавит только недостающие таблицы, данные не затрагиваются).
Все проверки окружения (модели, размерность эмбеддинга, БД) выполняются **до** начала долгой работы.

`scripts\demo_populate_db.py` - упрощённый демонстрационный скрипт: он пишет в БД пути на файлы исходного датасета, минуя детектор и хранилище, и не ведёт учёта в `ingest_sources`.
Остановку и продолжение он поддерживает (уже загруженное определяется по пути файла). Для штатного наполнения используйте `ingest_images.py`.
Не запускайте `ingest_images.py` на той же папке поверх базы, заполненной демо-скриптом: `ingest_images.py` об этих записях не знает и создаст дубликаты.

## Проверка детектора на ваших изображениях

Если детектор на каких-то изображениях ничего не находит или рисует рамку на часть машины, `ml\detection\check_detector.py` показывает, в чём дело и что помогает:

```powershell
# кропы (например, VeRi): мешает порог, размер входа или масштаб машины в кадре?
python ml\detection\check_detector.py --images data\VeRi\image_test --limit 60

# то же на ONNX, который реально использует приложение
python ml\detection\check_detector.py --images data\VeRi\image_test --model ml\detection\exported\vehicle_detector.onnx --out runs\check_onnx

# размер рамок против разметки YOLO (например, валидация UA-DETRAC)
python ml\detection\check_detector.py --images <папка кадров> --gt-labels <папка разметки> --limit 200
```

Скрипт вызывает YOLO так же, как `DetectorService`, и печатает итог по каждому варианту (порог, `imgsz`, масштаб) и вывод. В папке `runs\check_detector` остаются `summary.json` и контактные листы `sheet_*.jpg` с рамками (зелёная: достоверность не ниже порога приложения, оранжевая: ниже, синяя: разметка).
Перебор `imgsz` возможен только для `.pt`: у ONNX размер входа зафиксирован при экспорте.

## Развёртывание (Docker)

Целевая среда: Ubuntu 22.04, Docker Engine с Compose v2. Минимум по ТЗ: 4 ядра CPU, 16 ГБ ОЗУ.

1. **`.env`** в корне проекта (шаблон - `.env.example`): `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `ADMIN_API_KEY` (свой токен администратора). Пароль БД без символов `@ / : ? #`: он входит в URL подключения. Порт интерфейса по умолчанию 8080, меняется через `APP_PORT`.
2. **Модели** (в git их нет) положите в `ml/detection/exported/vehicle_detector.onnx` и `ml/reid/exported/reid_embedder.onnx`. Они монтируются в контейнер только для чтения.
3. **Запуск** из корня проекта: `docker compose up -d --build`. Первая сборка долгая (PyTorch и ultralytics), следующие идут из кэша.
4. **Проверка:** `http://localhost:8080/health` должен вернуть `"status": "ok"`; интерфейс - на `http://localhost:8080`.

| Задача | Команда |
|---|---|
| Логи backend | `docker compose logs backend --tail 60` |
| Остановить (данные сохраняются) | `docker compose down` |
| Обновить после правки кода | `docker compose up -d --build` |
| Резервная копия БД | `docker compose exec -T db pg_dump -U <пользователь> -d <база> > backup.sql` |

Данные лежат в томах `pgdata` (БД) и `storage` (изображения наблюдений и временные загрузки) и переживают пересоздание контейнеров. **`docker compose down -v` удаляет их безвозвратно.** Запускайте compose из корня проекта: имя папки задаёт имя проекта, а значит и имена томов.

Backend наружу не публикуется: интерфейс и API доступны через nginx на одном адресе. Замеры быстродействия работают и в этом режиме: `python scripts/benchmark_api.py <кадры> --url http://localhost:8080`.

**GPU-профиль** (ТЗ 1.1.1.2): `docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build`. Нужны драйвер NVIDIA и NVIDIA Container Toolkit. Профиль подготовлен, но на оборудовании с GPU не проверялся, поэтому GPU-бюджеты ТЗ (кроп 3 мс, эмбеддинг 100 мс) не измерены.

**Демо-данные (VeRi).** Записи, добавленные `demo_populate_db.py`, хранят пути на файлы датасета на хосте. Чтобы у них отображались изображения в контейнере, смонтируйте датасет в `backend` (`- ./data/VeRi/image_test:/app/data/veri/image_test:ro`) и один раз обновите пути в БД (UPDATE observations
SET image_path = '/app/data/veri/image_test/' || regexp_replace(image_path, '^.*[\\/]', ''),
    crop_path  = '/app/data/veri/image_test/' || regexp_replace(crop_path,  '^.*[\\/]', '')
WHERE image_path NOT LIKE '/app/%';

SELECT image_path FROM observations ORDER BY created_at LIMIT 3;
SQL). Записи, добавленные через интерфейс, этого не требуют.

## Конфигурация

- Все настройки - в `.env` в корне проекта; backend находит его независимо от
  того, из какой папки запущен.
- Относительные пути (модели, хранилище файлов) считаются **от корня проекта**.
- Сохранение и удаление наблюдений требуют заголовок `X-Admin-Token` со значением
  `ADMIN_API_KEY` (интерфейс запросит токен сам при первом таком действии).
- `SEARCH_HISTORY_MAX_ITEMS` - сколько последних поисков хранить (по умолчанию 500).
- `CORS_ORIGINS` принимает только JSON-массив. В штатной схеме он не нужен.

```powershell
pip install -r requirements-test.txt
pytest
```
Тесты, которым нужен настоящий PostgreSQL (`test_repository`, `test_create_indexes`,
`test_startup_checks`, `test_search_history_integration`, `test_ingest_service`, `test_ingest_cli`, часть `test_main`), используют **отдельную** БД из

```bash
docker compose exec db psql -U vehiclereid -d vehiclereid -c "CREATE DATABASE vehiclereid_test;"
docker compose exec db psql -U vehiclereid -d vehiclereid_test -c "CREATE EXTENSION IF NOT EXISTS vector;"
```
Тесты запускаются **из корня проекта**.

Версии зависимостей закреплены: Python-пакеты - в `constraints.txt` (получен на Linux, Python 3.12, где проходят все тесты; нужен Docker и CI:
`pip install -r backend/requirements.txt -c constraints.txt`, локально на Windows ставить с ним необязательно), npm-пакеты - в `frontend/package-lock.json`
(`npm ci` ставит ровно их). CI (`.github/workflows/tests.yml`) собирает среду именно по ним и дополнительно проверяет сборку фронтенда. При push в GitHub их выполняет CI
(`.github/workflows/tests.yml`, с настоящим PostgreSQL+pgvector).

## Частые проблемы

| Симптом | Причина и что делать |
|---|---|
| Сервер не стартует: «Не найдены файлы моделей» | Нет ONNX-файла. В сообщении указано, какой именно и какой командой его получить (шаг 5) |
| Сервер не стартует: «Размерность эмбеддинга (N) не совпадает (512)» | Модель экспортирована с другим `--embedding-dim`. Переэкспортируйте или меняйте схему БД |
| Сервер не стартует: «не смогла обработать тестовое изображение» | `REID_IMAGE_HEIGHT/WIDTH` не совпадают с `--imgsz` при экспорте |
| `/health`: `degraded` | Смотрите `problems`: чаще всего не запущена БД или не выполнен `db\create_table.py` |
| `ModuleNotFoundError: No module named 'backend'` | Команда запущена не из корня проекта |
| Поиск отвечает 503 | Причина - в консоли `uvicorn` (полный traceback). Чаще всего БД или размерность эмбеддинга |
| `password authentication failed` | Том БД создан со старым паролем: `docker compose down -v` и заново (удалит данные) |
| `Connect call failed ... 5433` | Контейнер не поднят или порт не совпадает с `DATABASE_URL`: `docker compose ps`; на Windows помогает `wsl --shutdown` и повторный `up` |
| Запросы к API «перехватывает» посторонний сервер (редирект на чужие страницы, 307) | Порт 8000 занят другим процессом: `netstat -ano \| findstr :8000`; в WSL - `docker ps`, `sudo ss -tulpn \| grep :8000` |
| В браузере остался старый интерфейс | `Ctrl+Shift+R`; при необходимости DevTools - Application - Clear site data |
| `npm` не найден в PowerShell | Установить Node.js LTS системно (`winget install OpenJS.NodeJS.LTS`), открыть новое окно терминала |
